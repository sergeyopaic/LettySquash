# Letty Squash — план перехода на реальный бэкенд

Дата: 2026-08-03
Статус: **дизайн согласован, реализация не начата**. Документ фиксирует решения, принятые в обсуждении, чтобы вернуться к ним при переходе с demo/localStorage-версии на реальные данные (реальные клубы, владельцы, менеджеры, игроки).

---

## 1. Почему не localStorage

Сейчас всё состояние приложения (`SquashContext.tsx`) живёт в `localStorage` одного браузера — без бэкенда, без авторизации, `CLUBS_LIST` захардкожен в коде. Это нормально для демо/личного использования, но не подходит, когда:
- к администрированию подключаются реальные владельцы и менеджеры разных клубов;
- данные должны переживать смену устройства/браузера;
- нужно разграничение прав между разными людьми на одни и те же данные.

## 2. Рекомендуемый стек

- **Postgres** как СУБД — данные приложения принципиально реляционные (клуб → игроки → матчи → игры/решения/pointLog, соревнования → участники), а не документные.
- **Supabase** как managed-платформа поверх Postgres — Auth, Row Level Security (RLS), REST/realtime из коробки, щедрый бесплатный тариф, не нужно поднимать и обслуживать отдельный сервер.
- **Row Level Security (RLS)** — права проверяются на уровне базы данных, а не только в коде фронтенда. Это критично при нескольких независимых администраторах разных клубов: менеджер физически не может прочитать/изменить чужой клуб, даже если найдёт способ обойти UI.
- Фронтенд (Vite/React) остаётся статикой (Vercel/Netlify/Cloudflare Pages), обращается к Supabase напрямую из браузера — отдельный backend-сервер не нужен, безопасность обеспечивает RLS.
- `SquashContext` уже сегодня — единственная точка доступа к данным в приложении. Миграция сводится к замене localStorage-чтений/записей внутри контекста на Supabase-запросы; компоненты (Dashboard, PlayersView, ScoreboardView и т.д.) менять почти не придётся.

## 3. Роли и права доступа

| Роль | Права |
|---|---|
| **Public** (без логина) | Читает всё: составы всех клубов, историю матчей — без ограничений. |
| **Authenticated** (любой одобренный аккаунт) | + может создавать (репортить) матчи между любыми двумя игроками в системе. |
| **Player** (игрок с аккаунтом) | + может подтверждать/оспаривать матчи со своим участием. |
| **Manager** | + полное редактирование/удаление матчей, игроков, соревнований своего клуба; может одобрять заявки на регистрацию новых игроков в свой клуб; может подтверждать матчи за игроков своего клуба (с аккаунтом или без). **Не может** управлять составом менеджеров/владельцем клуба. |
| **Owner** | = Manager + может назначать/снимать менеджеров своего клуба. |
| **Creator** (супер-админ, вы) | Абсолютно всё, во всех клубах: создаёт и удаляет клубы, назначает Owner'а клуба, может действовать за любого игрока/клуб. |

### Разграничение внутри "управления людьми"
- **Одобрение заявки новой регистрации игрока** в клуб — доступно Creator, Owner **и** Manager (любой администратор клуба).
- **Назначение/снятие роли Manager** — только Owner или Creator. Manager не может управлять другими менеджерами.

## 4. Регистрация пользователей

Открытой self-регистрации нет — посторонних людей в системе быть не может.

1. Человек регистрируется в приложении и выбирает клуб, к которому хочет присоединиться.
2. Заявка уходит Creator/Owner/Manager этого клуба.
3. Аккаунт создаётся/активируется только после одобрения — и на этом же шаге привязывается к существующей записи игрока в ростере клуба (если она уже была заведена клубом) либо создаёт новую.

## 5. Жизненный цикл клуба

- Клуб может создать **только Creator** (иначе не бывает Owner'а без клуба — курица и яйцо).
- Creator вручную назначает Owner'а созданного клуба; дальше Owner сам приглашает менеджеров и настраивает клуб.
- Удалить клуб может **только Creator**.

## 6. Жизненный цикл матча: "репорт → подтверждение"

Ключевое архитектурное решение обсуждения. Защита сдвинута с момента **создания** матча на момент, когда он становится **официальным**.

### Правила
1. **Создать (зарепортить) матч может почти кто угодно** — оба участника, менеджер/owner любого из вовлечённых клубов, либо вообще любой залогиненный (одобренный) пользователь — например, третий друг-судья, у которого нет отношения ни к одному из играющих. Матч сохраняется со статусом `PENDING_CONFIRMATION`.
2. Матч **не влияет на статистику/рейтинг**, пока оба участника-игрока не подтвердят результат.
3. Для каждого из двух "слотов" участника подтверждение может дать:
   - сам игрок (если у него есть аккаунт и он залогинен) — путь по умолчанию;
   - Manager/Owner клуба **этого конкретного игрока** — независимо от того, есть у игрока аккаунт или нет, и независимо от того, ответил ли он сам;
   - Creator — всегда, за любого игрока в любой момент.
4. Матч становится `CONFIRMED`, когда **оба слота** подтверждены — не важно, кем именно из допустимой цепочки.
5. Если участник **оспаривает** матч — статус `DISPUTED`, разрулить (подтвердить/поправить/удалить) может Manager/Owner/Creator.
6. **После подтверждения** редактировать/удалять матч могут только Manager/Owner/Creator — не сами игроки в одиночку (иначе участник мог бы задним числом поменять уже официальный проигрыш на победу).

### Почему так, а не через явное назначение арбитра или галочку "разрешить клубу судить мои матчи"
Оба варианта обсуждались и были отклонены:
- **Явное назначение арбитра при старте матча** — рабочее решение, но создаёт трение (нужно второе устройство или передавать телефон/заранее договариваться).
- **Постоянная галочка "любой из клуба может судить мои матчи"** — статическое разрешение без привязки к конкретному результату; открывает дорогу к накрутке фиктивных побед.

Схема "открытое создание + обязательное подтверждение обеими сторонами" закрывает все обсуждённые сценарии (три друга/один судит, interclub, накрутка статистики) одним универсальным правилом, без специальных веток логики под каждый случай.

## 7. Набросок схемы данных

Ориентировочные таблицы (уточняются при реализации):

```
clubs               (id, name, city, country, country_flag)
users               (id [= auth uid], name, email, is_super_admin)
players             (id, name, club_id FK, user_id FK nullable, skill_grade, country_code, handedness, avatar_bg_color, created_at)
club_admins         (user_id FK, club_id FK, role: 'owner' | 'manager')
pending_registrations (id, applicant_user_id or email, club_id FK, status: 'pending'|'approved'|'rejected', reviewed_by FK, reviewed_at)

matches             (id, player1_id FK, player2_id FK, date, p1_games_won, p2_games_won,
                      games jsonb, decisions jsonb, point_log jsonb,
                      match_format, match_type, target_points,
                      status: 'PENDING_CONFIRMATION' | 'CONFIRMED' | 'DISPUTED' | 'COMPLETED',
                      winner_id, total_duration_seconds, notes, created_by FK)
match_confirmations (match_id FK, participant_slot: 'p1'|'p2', confirmed_by_user_id FK, confirmed_at)

competitions        (id, name, format, status, club_a_id FK nullable, club_b_id FK nullable,
                      participant_ids uuid[], created_by FK, created_at)
```

`match_confirmations` — не два булевых флажка на `matches`, а отдельная таблица с логом: кто именно подтвердил за какого участника и когда. Даёт полноценный аудит на случай споров ("менеджер подтвердил за игрока, который потом сказал, что матча не было").

### Набросок RLS-политик
- `SELECT` на `clubs`/`players`/`matches`/`competitions` — открыто всем (`true`), включая анонимов.
- `INSERT` на `matches` — `auth.uid() is not null` (любой одобренный аккаунт).
- `UPDATE`/`DELETE` на `matches` — только manager/owner клуба одного из участников, либо `is_super_admin`.
- `INSERT` на `match_confirmations` — `auth.uid()` совпадает с игроком этого слота, ИЛИ является manager/owner клуба этого игрока, ИЛИ `is_super_admin`.
- `INSERT`/`DELETE` на `clubs` — только `is_super_admin`.
- `INSERT`/`DELETE` на `club_admins` (роль owner/manager) — только owner этого клуба или `is_super_admin`.
- `UPDATE` (approve/reject) на `pending_registrations` — owner/manager/`is_super_admin` клуба, к которому пришла заявка.

## 8. План миграции (по фазам, не одним большим переписыванием)

1. Завести Supabase-проект, спроектировать схему и RLS-политики.
2. Экраны авторизации: регистрация с выбором клуба и статусом "ожидает одобрения", логин.
3. UI управления клубом/админами: Creator создаёт клубы и назначает Owner'ов; Owner приглашает менеджеров; одобрение/отклонение заявок на регистрацию.
4. Замена localStorage-вызовов в `SquashContext` на Supabase-запросы (players/matches/competitions/settings) — компонентный слой почти не меняется, т.к. контекст уже сегодня единая точка доступа к данным.
5. UI жизненного цикла матча: список "матчи, ожидающие вашего подтверждения", кнопки подтвердить/оспорить.
6. Решить обработку матчей, которые никогда не подтверждают (см. открытые вопросы).
7. (Позже, опционально) Само-обслуживание игроков (редактирование своего профиля), режим турнира с заранее назначенными судьями с немедленными правами редактирования.
