# Аудит проекта Letty Squash

Дата: 2026-08-03
Объём: полный обзор `src/` (~9300 строк, 29 файлов) — состояние приложения (context), модель данных, представления, модалки, live-scoreboard и визуализации.

Отчёт не включает два бага, найденных и уже исправленных в этой же сессии до аудита:
- `addPlayer()` не проставлял `clubId` новому игроку → все новые игроки утекали в клуб Remuera (c2).
- `PlayerProfileModal`: счёт матча показывался в порядке `player1:player2` вместо перспективы просматриваемого игрока, не было названия клуба.

---

## 1. Сильные стороны

- **Модель данных внутренне непротиворечива.** В `mockData.ts` все 16 игроков имеют явный `clubId`, все ссылки `player1`/`player2` в матчах совпадают с комментариями, `winnerId`/`p1GamesWon`/`p2GamesWon` согласованы на уровне игр и матча, включая межклубные (interclub) встречи.
- **Чистая навигационная прослойка.** `App.tsx` и `NavigationTabBar.tsx` — без мёртвых обработчиков, без неиспользуемых пропсов, переключение вкладок и модалок реализовано единообразно.
- **Корректная фильтрация по клубам.** Сама логика `getPlayersForClub` / `getMatchesForClub` / `computePlayerStats` в `clubUtils.ts` работает правильно — проблемы обнаружены только в местах, которые её игнорируют (см. ниже).
- **Даты обрабатываются аккуратно.** `formatMatchDateGroup` в `dateUtils.ts` сравнивает календарные поля (день/месяц/год) с обеих сторон, корректно обрабатывает переход через границы месяца/года.
- **Разумная архитектура для размера проекта.** React Context вместо избыточного Redux/Zustand, чёткое разделение `context/ components/ utils/ data/ types/` — не переусложнено.
- **TypeScript почти везде.** Определены доменные интерфейсы (`types/squash.ts`), большинство компонентов типизированы; проблемы — точечные утечки `any` (см. §2).

## 2. Критические баги

### 2.1. Решение STROKE тихо теряется из истории матча
**`src/context/SquashContext.tsx:389-415` (`recordDecision`)**
`recordDecision` вызывает `setActiveMatchState({...activeMatchState, match: {...decisions}})`, а затем для `STROKE` сразу вызывает `recordPoint()`. `recordPoint` берёт `match` из того же **устаревшего** замыкания `activeMatchState` (а не через функциональный апдейтер), строит `updatedMatch` на основе этого устаревшего объекта и снова вызывает `setActiveMatchState` — перезаписывая первое обновление.
**Эффект:** при каждом STROKE-решении запись пропадает из `match.decisions`, сохраняется только изменение счёта. YES_LET/NO_LET сохраняются нормально, т.к. не вызывают `recordPoint`.

### 2.2. «Create Competition» ничего не сохраняет
**`src/components/NewCompetitionModal.tsx:171-186`**
`executeCreate()` только показывает тост и закрывает модалку. Нигде в `SquashContext` нет состояния `competitions`/сеттера для него. Весь флоу создания соревнования — бутафория, результат никуда не пишется.

### 2.3. AdvancedStatsModal игнорирует активный клуб полностью
**`src/components/AdvancedStatsModal.tsx:65-71`**
Заголовок жёстко хардкодит `"Devonport Squash Club • Auckland"` независимо от выбранного клуба, а сама таблица статистики берёт ВСЕХ игроков/матчи из контекста без какой-либо клубной фильтрации. Глобальные данные подписываются как данные одного конкретного клуба — прямое противоречие остальной части приложения, где клубный скоуп соблюдается.

### 2.4. «Rally Flow» показывает выдуманные данные как реальные
**`src/components/MatchDetailModal.tsx:43-77`**
`calculateGameRallyRibbon` читает `(match as any).history`, но у завершённых `SquashMatch` такого поля никогда не бывает (`history` существует только в переходном `LiveMatchState`, и `finishActiveMatch` в `SquashContext.tsx` его не копирует). В результате `gameHistory` всегда пуст, и панель «Rally Flow» для абсолютно любого реального матча тихо уходит в псевдослучайную симуляцию — пользователю показывают фейковую последовательность розыгрышей, выдавая её за настоящую.

## 3. Серьёзные баги

### 3.1. Interclub-формат соревнования игнорирует реальный ростер
**`src/components/NewCompetitionModal.tsx:51-108`**
Конфигуратор 4×4 Interclub берёт данные из хардкод-объекта `MOCK_CLUB_ROSTERS`, а не из реальных `players` (`useSquash()` / `getPlayersForClub`). Не видит изменений ростера, новых игроков, и даже собственное состояние `selectedPlayerIds` для этого формата не используется. Это уже **третья** независимая копия «ростера клубов» в проекте (после `mockData.ts` и удалённой в этой сессии копии в `DashboardView.tsx`).

### 3.2. Ничья засчитывается как поражение обоим игрокам
**`src/context/SquashContext.tsx:542-569` + `clubUtils.computePlayerStats`**
Если `finishActiveMatch` вызывается без `winnerId` (матч завершён вручную/досрочно при равном счёте), фолбэк в `computePlayerStats` (`p1GamesWon > p2GamesWon` / иначе поражение) не находит победителя ни по одному условию — оба игрока получают запись поражения по одному и тому же матчу.

### 3.3. Undo оставляет «призрачную» запись игры
**`SquashContext.tsx:311-317` vs `417-445` (`undoLastAction`)**
При отмене выигрышного за игру очка восстанавливаются `p1GamesWon`/`p2GamesWon`/`currentGameIndex`, но добавленный в `match.games` `GameResult` не удаляется. `games.length` расходится с `p1GamesWon + p2GamesWon`; при повторной победе в той же игре может появиться дубликат с тем же `gameNumber`.

### 3.4. Приложение падает при повреждённом localStorage
**`SquashContext.tsx:68-86`**
`JSON.parse(localStorage.getItem(...))` для всех трёх ключей вызывается без `try/catch` прямо в инициализаторе `useState`. Любое повреждённое/вручную изменённое значение — и всё приложение падает без возможности восстановления.

### 3.5. Старые локальные данные без `clubId` навсегда «залипают» в Remuera
**`clubUtils.ts:7-16`, остаточный риск после фикса `addPlayer`**
Фолбэк `getPlayerClubId` — это хардкод-угадывание клуба по префиксу `id`, подогнанное под 16 моковых игроков. У игроков, сохранённых в `localStorage` **до** сегодняшнего фикса `addPlayer`, `clubId` отсутствует, и они навсегда (без миграции) будут резолвиться в `c2`, даже после того как баг создания новых игроков исправлен.

## 5. Технический долг / code smell

- **`RallyProgressionChart.tsx` — 1190 строк полностью мёртвого кода.** Компонент нигде не импортируется за пределами собственного файла (подтверждено grep’ом), включая демо-секцию внизу файла.
- **`SquashCourtDiagrams.tsx:1235`** содержит собственный `export default function App()` — брошенная демо-страница ~115 строк, никогда не подключаемая к реальному `App.tsx`. Опасное совпадение имени с настоящей точкой входа.
- **Нет общего компонента `Modal`.** Оверлей / обработчик Escape / кнопка закрытия вручную продублированы в 8+ модалках (`AddPlayerModal`, `MatchDetailModal`, `NewMatchModal`, `NewCompetitionModal`, `SettingsModal`, `AdvancedStatsModal`, `ClubSelectorModal`, `PlayerProfileModal`, `HowToPlayModal`, `HowToUseAppModal`).
- **Дублирование логики форматирования:** `formatDuration` реализована отдельно в `DashboardView.tsx` и `MatchHistoryView.tsx`; `formatMatchDuration`/`getMatchDurationParts` в `dateUtils.ts` дублируют друг друга.
- **Мёртвый ручной инкремент статистики** в `finishActiveMatch` (`SquashContext.tsx:549-563`) — полностью перекрывается `computedPlayers` (через `computePlayerStats`) при каждом рендере, но всё равно пишет неверные числа в сырой `players` в `localStorage`.
- **Типобезопасность:** `LiveMatchState.history: any[]`, `let interval: any`, колбэки `(prev: any) =>` — реальная форма `historyEntry` не совпадает с объявленным (но нигде не используемым) типом `PointEvent` в `types/squash.ts`.
- **Версионирование localStorage без миграций.** Ключи `_v4`/`_v1` — при следующем бампе версии старые данные просто осиротеют, вместо явной миграции/очистки.
- **`GRADE_RANKS`/`getGradeRank`** определены прямо внутри `NewCompetitionModal.tsx`, а не в `utils/`, что затрудняет переиспользование в `PlayersView`/`AdvancedStatsModal`.
- **`selectedPlayerIds` в `NewCompetitionModal`** инициализируется один раз при первом монтировании — так как модалка не размонтируется (просто возвращает `null`), игроки, добавленные позже, никогда не попадают в «выбраны по умолчанию» для форматов League/Playoff/Elimination.
- **`countries.ts`** — 76 стран, разумно для демо, но не хватает отдельных England/Wales/Scotland (важно именно для сквоша), Бангладеш/Шри-Ланки и др. `DEFAULT_COUNTRY = WORLD_COUNTRIES[0]` — позиционная зависимость, при переупорядочивании массива дефолт молча сменится.
- **Метрика «rallies»** в `ScoreboardView.tsx:882` на деле считает сумму всех очков за матч, а не количество физических розыгрышей (леты/страйки без изменения счёта не учитываются) — вводящее в заблуждение название.

## 6. Рекомендации по приоритету

1. **Исправить `recordDecision`/`recordPoint`** — использовать функциональный апдейтер `setActiveMatchState(prev => ...)` вместо чтения устаревшего замыкания; иначе решения STROKE продолжат теряться.
2. **Решить, что делать с `NewCompetitionModal`** — либо реализовать реальное сохранение (`competitions` в контексте + связка с реальным ростером через `getPlayersForClub`), либо явно пометить фичу как «Coming soon» и убрать вводящий в заблуждение UI.
3. **Починить `AdvancedStatsModal`** — принимать `activeClub` и фильтровать данные, убрать хардкод названия клуба.
4. **Убрать фейковую Rally Flow-симуляцию** из `MatchDetailModal` или явно подписать её как «примерная визуализация», раз реальных данных о розыгрышах не существует.
5. **Обернуть `JSON.parse` в localStorage-инициализаторах в try/catch** с откатом на `INITIAL_PLAYERS`/`INITIAL_MATCHES` — дешёвая защита от полного краха приложения.
6. **Удалить мёртвый код**: `RallyProgressionChart.tsx` целиком (или подключить, если он всё же нужен), демо-`App` внутри `SquashCourtDiagrams.tsx`, `DEFAULT_SETTINGS`.
7. **Добавить сортировку по дате** для списков матчей на Dashboard и в History, унифицировать формулу определения победителя в один общий хелпер (`clubUtils.ts` — подходящее место).
8. Более низкий приоритет: общий компонент `Modal`, вынос общих форматтеров длительности, единая цветовая палитра для чартов.
