## 1. Сетка для остальных турниров (главный пункт)

Сейчас автогенерация фикстур работает **только** для Interclub 4×4 (ранг vs ранг, замороженный состав). Остальные 4 формата в `CompetitionDetailModal` показывают заглушку «fixture generation isn't built yet»:

- [x] **League (Round-Robin)** — каждый с каждым, генерация расписания. *(`src/utils/fixtureUtils.ts` — `generateRoundRobinFixtures`, подключено в `NewCompetitionModal`; попутно поправил в `CompetitionDetailModal`: лейбл "Rank #N" теперь "Fixture #N" для не-interclub форматов, и заблокировал старт матчей на заархивированных турнирах.)*
- [x] **Groups + Knockout** — распределение по группам + плей-офф сетка после группового этапа. Мин. 4 участника, макс. 16 (та же граница введена и для Single/Double Elimination). *(`src/utils/fixtureUtils.ts` — `computeGroupCount`: число групп = наименьшее, при котором каждая группа ≥3 человек (цель — группы по 3-4, как в реальных турнирах); отсюда решение для "неудобных" 7/11/13 — 7→2 группы (4+3), 11→3 группы (4+4+3), 13→4 группы (4+3+3+3), т.е. никогда не получается вырожденная группа из 1-2 человек. Состав групп — змейкой (snake draft) по посеву через грейд, чтобы сильные не собрались в одной группе. Каждая группа — обычный `generateRoundRobinFixtures`. Топ-2 из каждой группы (топ-4, если группа одна — поле в 4-5 человек) выходят в плей-офф-сетку, посеянную "все победители групп → все вторые места", с байами при недостатке до степени двойки — та же механика, что в Single Elimination. Поскольку составы плей-офф-пар неизвестны при создании турнира (зависят от итогов группы), фикстуры плей-офф хранят не игрока, а "занявший место R в группе G" (`player1GroupIndex`/`player1GroupRank`), которое `resolveFixturePlayers` разрешает, как только все матчи этой группы сыграны.* В `CompetitionDetailModal` — вкладки по группам (мини-таблица + матчи группы) и отдельная сетка плей-офф.
- [x] **Single Elimination** — генерация сетки на выбывание, посев (seeding) по грейду. *(`src/utils/fixtureUtils.ts` — `generateSingleEliminationBracket`: стандартный seed order, поле дополняется до ближайшей степени двойки байами, которые достаются топ-сидам; `resolveFixturePlayers`/`getFixtureWinnerId` разрешают игроков следующих раундов "на лету" по победителям предыдущих, ничего не хранится заранее. Визуальная сетка с колонками по раундам и автоматическим отображением чемпиона — в `CompetitionDetailModal`.)*
- [x] **Double Elimination** — сетка с winners/losers-бранчами. *(`src/utils/fixtureUtils.ts` — `generateDoubleEliminationBracket`: winners-сетка как в Single Elimination (байи топ-сидам), losers-сетка собирается раунд за раундом (drop-in + consolidation, как в классических DE-сетках), с общим `pairEntrantsWithByes` для нечётных/неровных остатков — сходится ровно к одному чемпиону losers-сетки при любых байах. Grand Final — один решающий матч (без "bracket reset": второй матч при победе стороны из losers-сетки не моделируется, т.к. это фикстура, которая существует только условно от результата — не вписывается в модель "все фикстуры заморожены при создании турнира"). Визуально — Winners Bracket / Losers Bracket отдельными колонками + отдельная карточка Grand Final, в `CompetitionDetailModal`.*
  — Попутно нашёл и исправил реальный баг: `findFixtureMatch` определял "матч этой фикстуры" по паре игроков, что ломалось при легитимном реванше (Grand Final против того же соперника, что и в финале winners-сетки, — самый обычный сценарий DE; также задевало уже существующий двухкруговой League — вторая встреча пары показывала результат первой). Теперь `SquashMatch` хранит `fixtureSlot`, и поиск матча фикстуры сначала ищет по слоту, только потом — по паре игроков (для старых данных без `fixtureSlot`).*
- [ ] **Замены игроков в Interclub** — отдельный разговор, который мы отложили ("об этом чуть попозже побеседуем"). Нужно решить: как редактировать уже сгенерированные fixture-пары после создания турнира.

## 2. Найденные баги (реальные, не архитектурные)

- [ ] **Interclub-матчи не попадают в Club Rating.** `computeClubRatings` вызывается с `players`, отфильтрованными по ОДНОМУ клубу (`getPlayersForClub`), но с `matches`, где встречаются игроки ДРУГОГО клуба (interclub). Rating-функция делает `if (!p1 || !p2) continue` — если оппонента нет в переданном списке игроков, весь матч пропускается целиком, включая обновление рейтинга ДОМАШНЕГО игрока. То есть `isRated: true` на interclub-матчах сейчас ни на что не влияет. Нужно передавать в `computeClubRatings` игроков ОБОИХ клубов, участвующих в матчах, а не только домашнего.
  — `src/utils/ratingUtils.ts`, вызовы в `DashboardView.tsx:77`, `PlayersView.tsx:20`, `PlayerProfileModal.tsx:47`
- [ ] **Архивные турниры не защищены от старта матчей.** `CompetitionDetailModal` не проверяет `competition.status === 'COMPLETED'` — на заархивированном турнире кнопки «Start Refereeing» по-прежнему живые и создают реальные матчи.
- [ ] **«PARS 11» захардкожен в UI**, хотя `targetPoints` теперь настраивается за турнир (11 или 15):
  - `ScoreboardView.tsx:274` — надпись "PARS 11" вместо `match.targetPoints`.
  - `getLettyCommentary` (`ScoreboardView.tsx:135-141`) — тай-брейк/game-ball комментарии зашиты на `>= 10`, должно быть `match.targetPoints - 1`.
  - `HowToPlayModal.tsx:131,206-217`, `HowToUseAppModal.tsx:112` — те же самые "PARS 11" как единственное фиксированное правило.
